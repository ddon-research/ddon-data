[[purpose]]
== Purpose
This script runs a C# CLI (Arrowgene.Ddon.Cli.exe) against many YAML files produced from pcapng/pcap streams.
It runs multiple CLI instances in parallel, captures per-job logs.

[[requirements]]
== Requirements

* GNU bash (recommended)
* coreutils: find, sed, grep, awk
* Optional but recommended: flock
* The target CLI binary (configured via `CLI_PATH` in the script)


[[config]]
== Configuration
Top-of-script variables you will change or override via environment:

* `CLI_PATH` — path to Arrowgene.Ddon.Cli.exe (update for your build)
* `KEYS_FILE` — default `keys/keys-all-in-one.csv`
* `STREAM_DIR` — default `encrypted_streams`
* `MAX_JOBS` — maximum concurrent CLI processes (env override). Defaults to detected CPU count.

Notes:

* The script creates a temporary directory (`mktemp -d`) for per-job logs and removes it on exit. To persist logs, set `tmpdir` to a permanent location and remove the `trap` that deletes it.
* Parallel CLI instances share one log file (`bin/Debug/net10.0/Logs/<date>.log.txt`); a job that loses the race crashes with `IOException ... being used by another process` and exit code 127, without output. The script still exits 0, so check every `JOB DONE` line and rerun failed streams with `MAX_JOBS=1`. To re-export a subset, hard-link the YAMLs into a short-named folder and set `STREAM_DIR` to it.

[[usage]]
== Usage

Run normally: `./run-parallel-packet.sh`

Run with tuned parallelism: `MAX_JOBS=6 ./run-parallel-packet.sh`

Per-job output (abbreviated):

* `==== JOB DONE: stream85_tcp11 (exit 0) ====`
* `file=...`
* `streamName=...`

[[concurrency]]
== Concurrency tuning

* Default: `MAX_JOBS` defaults to the number of logical CPUs.
* If CLI is I/O-bound, increasing `MAX_JOBS` can help. If CPU-bound, set `MAX_JOBS` to the number of physical cores or fewer.
* Test with small values first; reduce `MAX_JOBS` if the machine becomes unresponsive.

[[arrowgene-patches]]
== Required Arrowgene CLI patches

The annotated dumps in `decrypted_annotated/` are produced with a locally patched build of
`Arrowgene.Ddon.Cli` from the upstream clone
`C:\Users\morph\Documents\GitHub\Sehkah\Arrowgene.DragonsDogmaOnline.Upstream` (branch `develop`,
base `e2411fe8`, patches uncommitted). Build it with
`dotnet build Arrowgene.Ddon.Cli/Arrowgene.Ddon.Cli.csproj -c Debug`. An unpatched build skips the
affected packets with `Unable to parse structure for resolved packet ... Skipping.` and writes
`StructDump:` without a structure.

Why the structure patches are needed: `EntitySerializer.ReadServerResponse` reads `Result` as a
`u16` whenever `Error != 0`, but servers keep writing the full response (`Error` and `Result` as
`u32`, then the payload). Every field after `Result` is then read 2 bytes early: an empty list's
count becomes a huge number and parsing runs into the packet's block padding
(`EndOfStreamException`). The Season 3 client does not read past a non-zero `Error`
(for example `GROUP_CHAT_GET_MEMBER_LIST_RES` reader `0x809D80` in the PC 03040008 client), so the
patches stop the same way:

[source,csharp]
----
ReadServerResponse(buffer, obj);
if (obj.Error != 0) return obj;
----

[[splitting]]
== Splitting large dumps

`decrypted_annotated/` keeps files under 50 MiB. Split a larger dump at packet boundaries with:

----
./split-annotated.sh [--force] encrypted_streams/<stream>.yaml.annotated.txt [decrypted_annotated] [max_bytes]
----

It writes `<stream>_1.yaml.annotated.txt` ... `<stream>_N.yaml.annotated.txt` (or the unsuffixed
name if the dump fits), never cuts a packet in two, and verifies that concatenating the pieces
reproduces the input byte for byte before replacing anything. `--force` replaces the stream's
existing pieces. This replaces the manual `split -C 50M` plus moving cut-off packets by hand.

[[raw-export]]
== Exporting raw packets

`./decrypt-export-streams.sh [stream.yaml ...]` decrypts every stream (or the given ones) with the
same CLI (`CLI_PATH`, `KEYS_FILE`, `STREAM_DIR` as above) and writes one file per packet to
`decrypted_raw/<stream>/` (`OUT_DIR` overrides): header plus payload, named
`<pcap no>_<PacketId.Name>_<timestamp>.<group>_<id>_<sub>`. Names are the `Name` string of the
CLI's `PacketId` table, not the C# field name (they differ for 63.11.16: field
`C2S_63_11_16_NTC`, Name `S2C_63_11_16_NTC`, declared `PacketSource.Server` although the client
sends it). Streams run one at a time (shared log file); each YAML is copied to a temporary folder
because the CLI writes `<yaml>.annotated.txt` beside its input. A stream whose output folder exists
is refused, so exports of different builds never mix.

The current `decrypted_raw/` and the file names in `decrypted_json/` come from the patched build
above (Upstream `e2411fe8`, net10.0), exported 2026-11-01; they replace the 2024-05-13 export of an
older CLI. Differences, checked file by file (same 125 streams, same 146,891 files): 51 packet ids
renamed to the server's current names (1,958 files); timestamps with 100 ns precision instead of
milliseconds (.NET 7+ `DateTimeOffset.AddSeconds` no longer rounds); and the 43
`C2S_SERVER_GET_SERVER_LIST_REQ` (1.0.1) files now start with the 9-byte header like every other
file (the old ones held only the 7-byte payload). All other bytes are identical.
The 250 first-packet raws (84 `*.1_0_1`, 166 `*.44_0_1`) were replaced on 2026-11-01 by an export
with the fixed-key patch above (spec 006 T002d); the other files of that export were
byte-identical to the ones here.
On 2026-11-01 (spec 006 T002e) a full export with the relabelling patch above reproduced all
146,891 files: 146,766 byte-identical under the same name, the 125 server certificate notices

[[imhex-export]]
== Exporting packet structures with ImHex

The patterns, their includes, JSON conventions, evidence rules, per-type fit counts and open items
are described in `../research/03040008/packets/README.md`.

`./imhex-export.sh [--force] [--json-nonfinite=keep|null] <packet-filter> <pattern-name> [jobs]`
decodes the per-packet files in `decrypted_raw/<stream>/` with
`../research/03040008/packets/<pattern-name>-pattern.cpp` and writes
`decrypted_json/<stream>/<packet-file>.json`. Set `IMHEX` if ImHex is not on `PATH`; output paths
must stay under 260 characters for the Windows ImHex build. `./imhex-export.sh` without arguments
prints the options and every environment override.

A packet that fails writes `<packet-file>.json.err` and removes any `<packet-file>.json` an earlier
run left, so counts over `decrypted_json` never mix runs. plbatch parses every output with
nlohmann json: a float that is NaN or Inf comes out of the formatter as a bare `nan`/`inf`, which is
not valid JSON. Such files are counted as `nonfinite` and kept as printed (default
`--json-nonfinite=keep`, byte-identical to ImHex; `jq` rejects them) or written with `null` in
their place (`--json-nonfinite=null`). Output that is invalid for any other reason counts as
`badjson`, a failure. The ImHex path does not validate.

`<packet-filter>` selects the raw files three ways:

* `@`: the packet id the pattern declares in a `// packet-id: <group>.<id>.<sub>` header line
  (`./imhex-export.sh @ C2S_CONTEXT_35_5_16_NTC`). A pattern whose id another server shares names
  its packet in a `// packet-select: <name>` line, and `@` then takes only the files of that id whose
  name holds `_<name>_` (the login patterns `C2L_LOGIN_REQ`/`L2C_LOGIN_RES` share 0.1.1/0.1.2 with
  the game server's `CONNECTION_LOGIN`). `@` refuses an id that login-server (`C2L_`/`L2C_`) and
  game-server (`C2S_`/`S2C_`) files share when the pattern has no such line, since a shorter layout
  would still fit (spec 005 R2 F2; test: `research/03040008/packets/tests/imhex-export-select.sh`);
* `<group>.<id>.<sub>` (`35.5.16`): files whose name ends in `.35_5_16`;
* anything else: a substring of the file names, as before (files only: a matching directory name
  selects nothing).

The id forms do not depend on the packet name in the file name, which the CLI took from the
server's `PacketId` at export time: an outdated or "Unknown" name cannot hide packets from them.
Patterns without a nNetMsg payload (spec 005 P9, `include/Packet.hexpat`) export `fits`: the raw
files store no body length, so a decode fits when it ends within the last 15 bytes (cipher block
padding). A fit does not prove field widths: when the slack exceeds a field, a body that is that
field shorter (or longer, within the padding) fits as well (R1 F3; e.g. the 16-byte packets fit any
body of 0-7 bytes). Each pattern exports `paddingSize`, the slack, so counts can show it; such
widths rest on the PC writers, not on the fit. The nNetMsg patterns export `msgFits` (the message
ended exactly at its `len`) and, after the packet's last field, `fits` (padding of 15 bytes or
less). Patterns whose name gives the direction export `sourceOk`: the header source byte is 0x00
(client, C2S) or 0x34 (server, S2C).

String values in the JSON are UTF-8 JSON strings, written as is with the standard escapes (`\"`,
`\\`, `\n`, `\r`, `\t`, `\u00XX` for control characters); a byte that is not valid UTF-8 comes out
as `\u00XX`. There is no percent encoding since spec 006 T001d; the export before it, and ImHex
1.38.1 still, wrote every byte outside `[A-Za-z0-9-_.~]` as `%XX` (`"Rumi%20Amestris"`).

Two engines, same JSON byte for byte except for that string encoding:

* *plbatch* (default when built): `bash ../research/imhex/plbatch/build.sh` builds
  `../research/imhex/plbatch/build/bin/plbatch.exe`, PatternLanguage master `300d7388` (UTF-8
  strings; ImHex 1.38.1 embeds `fb6ea061`), with MSYS2 mingw64 (see `research/imhex/plbatch/README.md`). The script
  deals the file list into `jobs` shards (default `nproc`) and runs one plbatch process per shard;
  no process is started per packet. It takes the std library from `<imhex dir>/includes`
  (`IMHEX_INCLUDES` overrides). Set `PLBATCH` to another build, or `PLBATCH=none` for ImHex.
* *ImHex* (fallback): one `imhex --pl format` per packet, about 0.25-0.5 s each for process start
  and plugin init; default `nproc / 2` jobs, since every MSYS process creation slows down as more
  jobs fork at once (P3's export of 110,065 nNetMsg packets ran at about 6 packets/s).

Measured 2026-11-01 (client 03040008, contended machine): plbatch did 100 `S2C_LOBBY_LOBBY_DATA_MSG_NTC`
packets in 2.84 s ± 0.11 in one process (about 35/s; parsing the pattern costs ~25 ms per packet,
evaluation under 1 ms), against 534 ms ± 317 per packet for `imhex.exe`. On 3,028 packets (1,000
per nNetMsg type, all 8 `C2S_PARTY_SEND_BINARY_MSG_ALL_NTC`, P7's 20 samples) the JSON of both
engines was byte-identical (plbatch then at `fb6ea061`). Error logs (`.json.err`) differ in wording; plbatch adds the stack trace.

[[statistics]]
== Packet statistics

`./statistics-commands.sh [-k] [-f]` reads every dump in `decrypted_annotated/` in one pass and
rewrites, only after a successful run:

* `decrypted-tcp-streams-unique-{c2s,s2c,c2l,l2c}-packets-count.txt`: `(group.id.sub) NAME,count`;
* `packets-missing-structure-dumps.txt`: packet types without a C# structure (no `StructDump:` line);
* `packets-structure-parse-failures.txt`: packets whose structure failed to parse, with counts.

Only packet header lines are counted. It refuses to run when a stream exists both unsplit and as
`_N` pieces. The results mix CLI versions until every stream is re-exported with the same build:
packet names come from the CLI that produced each dump.
